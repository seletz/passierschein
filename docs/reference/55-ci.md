# CI

Die CI hat zwei Workflows für Prüfungen.
Dazu kommen der Release-Workflow und der signierte Snapshot.
Jeder Schritt ist genau ein `mise run <task>`.
`mise run tools:check` prüft diese Regel und die Pins der Actions für jeden Workflow.

## Was wo läuft

| Workflow | Runner | Auslöser | Inhalt |
|---|---|---|---|
| `ci.yml` (CI) | `ubuntu-latest` | jeder Pull Request, Push auf `develop` | `mise run check` mit allen portablen Tests, `build`, `docs:build`, `release:snapshot`, `release:sbom:check` |
| `macos.yml` (macOS) | `xcode-27` (macOS 27, arm64) | Push auf `develop`, jede Nacht, von Hand, Pull Requests nur bei passenden Pfaden | `build`, alle Go-Tests auf macOS (`test`), `app:build`, `app:test`, das Release-Bundle mit Ad-hoc-Signatur (`release:snapshot`, `release:app`, `release:app:sign`, `release:app:check`, `release:app:package`, `release:sbom:check`), `app:e2e`, `test:onepassword:ci` |
| `release.yml` (Release) | `ubuntu-latest` und `xcode-27` | Tag `v*` | Release mit signierter und notarisierter App ([Release](50-release.md#jobs-des-release-workflows)) |
| `signed-snapshot.yml` | `ubuntu-latest` und `xcode-27` | von Hand | Signatur und Notarisierung von `a38` und der App ohne Veröffentlichung |

Der macOS-Workflow wiederholt `mise run check` nicht.
Er prüft nur, was der Linux-Runner nicht kann:

- **darwin-Code in Go:** `mise run test` auf macOS führt auch die Dateien mit der Build-Bedingung `darwin` aus: das 1Password-Backend mit dem SDK, seine Verdrahtung in `a38 serve` und die Peer-Daten des Sockets.
- **Freigabe-App:** Bau, Swift-Tests und der Ablauf mit echten Prozessen ({{ ref("T14") }}, Teil 1). Der Ablauf nutzt die gefälschte Authentifizierung und nie Touch ID.
- **Release-Bundle:** `Passierschein.app` mit `a38` wie im Release, aber ad-hoc signiert (`APP_SIGN_ADHOC=1`, `APP_CHECK=adhoc`). Der Lauf prüft Aufbau, Reihenfolge der Signatur, Bezeichner, Hardened Runtime, ZIP und SBOM. Die Developer ID und die Notarisierung brauchen die Secrets und laufen nur in `release.yml` und `signed-snapshot.yml`.
- **1Password ({{ ref("T15") }}):** der Integrationstest gegen den Vault `passierschein.dev` mit dem Service Account der CI. Der Test liest nur.

Ein Lauf dauert etwa fünf Minuten; das Release-Bundle kostet etwa eine bis zwei Minuten mehr. `app:e2e` läuft in der grafischen Sitzung des Runners; die zwei kurzen Fenster öffnen sich dort.

Nicht automatisch prüfbar bleiben der echte Dialog von Touch ID und die Sicht unter OmniWM.
Offen sind Vollbild, Wechsel des Arbeitsbereichs, Zeitablauf und Meldungen ({{ ref("G33") }}) und der Praxistest eines echten Release auf dem Mac ({{ ref("G5") }}). Der signierte Snapshot mit der echten Developer ID ist am 2026-11-12 grün ([Lauf 43208639784](https://github.com/seletz/passierschein/actions/runs/43208639784)).

## Doku auf GitHub Pages

Der Workflow `pages.yml` baut die Doku nach jedem Push auf `develop` und
veröffentlicht sie auf GitHub Pages. Er läuft auf Linux und ruft nur
`mise run docs:build` auf. Die Site ist öffentlich, auch wenn das Repo
privat ist. Einzelheiten stehen unter [Release](50-release.md).

## Kosten

In einem privaten Repository zählt eine Minute auf macOS zehnmal so viel wie eine Minute auf Linux.
Deshalb startet ein Pull Request den macOS-Workflow nur, wenn er einen dieser Pfade ändert:
`app/**`, `internal/backend/onepassword/**`, `internal/approval/**`, `internal/token/**`, `internal/tokenfile/**`, `cmd/a38/**`, `go.mod`, `go.sum`, `mise.toml`, `.goreleaser.yml`, `scripts/**`, den Workflow selbst, `release.yml` und `signed-snapshot.yml`.
Ein neuer Push bricht den laufenden Lauf desselben Branches ab (`concurrency`).

## Caches

Kein Cache enthält ein Secret, `dist/` oder `$RUNNER_TEMP`.
Jeder Cache nutzt die gepinnte Action `actions/cache`.

| Workflow | Cache | Schlüssel |
|---|---|---|
| beide | Werkzeuge von mise (`mise-action`, `cache: true`) | Version von mise, `mise.toml` |
| macOS | dazu die Swift-Toolchain der App-Tasks (`cache_save_post`, eigener Präfix `mise-macos-swift-v1`) | wie oben |
| beide | Go-Module und Build-Cache von Go | `go.sum`, `go.mod`, `mise.toml`, je Betriebssystem |
| CI | Cache von golangci-lint | `go.sum`, `mise.toml`, `.golangci.yml` |
| CI | Cache von uv und `.venv` | `uv.lock`, `pyproject.toml`, `mise.toml` |
| macOS | Build-Ordner von SwiftPM `app/.build` | `app/Package.swift`, `mise.toml`, Quellen der App |

`app:build` baut aus dem Cache nur, was sich geändert hat.
Der Task legt das Bundle jedes Mal neu an und prüft das neue Release-Binary.

Gemessene Laufzeit eines Jobs (2026-11-12):

| Workflow | ohne Caches | kalt (Caches leer) | warm |
|---|---|---|---|
| CI (Linux) | 300 bis 480 s | 330 s | 117 s |
| macOS | 242 bis 280 s | 248 s | 130 bis 136 s |

Der Release-Snapshot und die Prüfung der SBOMs laufen weiter bei jedem Pull Request.
Sie sind die einzige Stelle, an der ein Pull Request alle vier Ziele baut, auch darwin.
Mit dem Build-Cache dauert der Snapshot warm etwa 15 Sekunden statt 90 bis 160 Sekunden.

Einmal brauchte der Aufbau des SDK-Clients auf dem macOS-Runner mehr als 30 Sekunden, und der Integrationstest scheiterte; der nächste Lauf war grün.
Der Test erlaubt deshalb 60 Sekunden je Aufruf.
Ein Fehler im Schritt „1Password integration test“ ist trotzdem zuerst ernst zu nehmen.

## Runner und Swift

- Die App-Tasks pinnen Swift 6.4.2 (Toolchain von swift.org über mise).
- Die Toolchain braucht das macOS-SDK aus Xcode. Das passende SDK ist Xcode 27.2.
- Stand 2026-11-12: Das Image `macos-26` (= `macos-latest`) hat Xcode bis 26.6. Nur das Image `xcode-27` hat Xcode 27.2 ([runner-images](https://github.com/actions/runner-images/blob/main/images/macos/xcode-27-arm64-Readme.md)).
- Der Workflow setzt `DEVELOPER_DIR=/Applications/Xcode_27.2.app/Contents/Developer`.

Risiken:

- `xcode-27` ist bei GitHub eine öffentliche Vorschau. GitHub kann das Image ändern.
- GitHub ersetzt eine Patch-Version von Xcode durch die nächste. Dann fehlt der feste Pfad, und der Job scheitert sofort an dieser Stelle. Die Abhilfe ist ein neuer Pfad im Workflow.

## Service Account der CI

Die CI nutzt einen eigenen Service Account, getrennt vom Service Account auf dem Mac.
Er darf nur den Vault `passierschein.dev` lesen.
Der Mensch kann ihn widerrufen, ohne den Daemon auf dem Mac zu berühren.

Das Secret des Repositorys heißt `OP_SERVICE_ACCOUNT_TOKEN`.
Anlegen, Setzen und Rotieren beschreibt die Anleitung [1Password-Backend einrichten](../how-to/30-1password-backend-einrichten.md#service-account-der-ci).

Im Lauf schreibt `mise run test:onepassword:ci` das Token aus der Umgebungsvariable `OP_SERVICE_ACCOUNT_TOKEN` in eine neue Datei unter `$RUNNER_TEMP` mit dem Modus `0600`.
Das Skript gibt das Token nie aus und löscht die Datei am Ende.
Die Maskierung von Secrets im Log von GitHub ist nur eine zweite Sicherung.
Fehlt das Secret, scheitert der Schritt mit einer klaren Meldung.
Ein übersprungener Test sähe grün aus und verdeckte einen Fehler.

## Rate Limits

1Password begrenzt die Anfragen eines Service Accounts ([Rate Limits](https://www.1password.dev/service-accounts/rate-limits)):

| Konto | Lesen je Stunde und Token | Anfragen je Tag und Konto |
|---|---|---|
| Business | 10.000 | 50.000 |
| Teams | 1.000 | 5.000 |
| 1Password, Families | 1.000 | 1.000 |

Das Tageslimit gilt für alle Service Accounts eines Kontos zusammen, also für den Mac und die CI.

Schätzung für einen Lauf des Integrationstests:

- Der Test macht 12 Aufrufe des SDK: einmal die Vaults für die Prüfung der Sichtbarkeit, einmal die Vaults beim ersten Auflösen, je Referenz die Items und ein Item (3 × 2), drei Lesezugriffe und die Items für das fehlende Item. Dazu kommt die Anmeldung des Clients.
- Wie viele Anfragen ein Aufruf des SDK erzeugt, dokumentiert 1Password nicht. Mit bis zu fünf Anfragen je Aufruf sind es höchstens etwa 70 Anfragen je Lauf.
- Der Fall mit kaputtem Token nutzt kein gültiges Token. Er zählt vermutlich nicht für das Konto.

Erwartete Läufe am Tag: einer in der Nacht, einige Pushes auf `develop`, einige Pull Requests mit passenden Pfaden; zusammen selten mehr als 20.
Das sind höchstens etwa 1.400 Anfragen am Tag, meist deutlich weniger.

- Business und Teams: weit unter dem Limit.
- 1Password und Families (1.000 am Tag für das ganze Konto): Im ungünstigsten Fall reicht das Limit nicht. Dann den Workflow seltener starten, zum Beispiel ohne Pull Requests.

Den Verbrauch zeigt `op service-account ratelimit passierschein-ci` im eigenen Terminal.
