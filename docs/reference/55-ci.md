# CI

Die CI hat zwei Workflows für Prüfungen.
Dazu kommen der Release-Workflow und der signierte Snapshot.
Jeder Schritt ist genau ein `mise run <task>`.
`mise run tools:check` prüft diese Regel und die Pins der Actions für jeden Workflow.

## Was wo läuft

| Workflow | Runner | Auslöser | Inhalt |
|---|---|---|---|
| `ci.yml` (CI) | `ubuntu-latest` | jeder Pull Request, Push auf `develop` | `mise run check` mit allen portablen Tests, `build`, `docs:build`, `release:snapshot`, `release:sbom:check` |
| `macos.yml` (macOS) | `xcode-27` (macOS 27, arm64) | Push auf `develop`, jede Nacht, von Hand, Pull Requests nur bei passenden Pfaden | `build`, `test:sdk-core`, alle Go-Tests auf macOS (`test`), `app:build`, `app:test`, das Release-Bundle mit Ad-hoc-Signatur (`release:snapshot`, `release:app`, `release:app:sign`, `release:app:check`, `release:app:package`, `release:sbom:check`), `app:e2e`, `test:onepassword:ci` |
| `release.yml` (Release) | `ubuntu-latest` und `xcode-27` | Tag `v*` | Release mit signierter und notarisierter App ([Release](50-release.md#jobs-des-release-workflows)) |
| `signed-snapshot.yml` | `ubuntu-latest` und `xcode-27` | von Hand | Signatur und Notarisierung von `a38` und der App ohne Veröffentlichung |

Der macOS-Workflow wiederholt `mise run check` nicht.
Er prüft nur, was der Linux-Runner nicht kann:

- **darwin-Code in Go:** `mise run test` auf macOS führt auch die Dateien mit der Build-Bedingung `darwin` aus: das 1Password-Backend mit dem SDK, seine Verdrahtung in `a38 serve` und die Peer-Daten des Sockets.
- **Kern des 1Password-SDK unter der Hardened Runtime ({{ ref("T30") }}):** `release:app:check` prüft, dass `a38` im Bundle genau das Entitlement aus `scripts/a38.entitlements` trägt und die App keines. `test:sdk-core` und `release:app:check` starten zudem `a38 selftest sdk-core`. Kein Token, kein Netz. Grenze: Der Runner setzt die Hardened Runtime für Code im Speicher nicht durch; auch `a38` ohne Entitlement läuft dort. Die Gegenprobe meldet dann „enforcement not active here“ als Warnung. Verlässlich ist auf dem Runner nur die Prüfung der Entitlements.
- **Freigabe-App:** Bau, Swift-Tests und der Ablauf mit echten Prozessen ({{ ref("T14") }}, Teil 1). Der Ablauf nutzt die gefälschte Authentifizierung und nie Touch ID.
- **Release-Bundle:** `Passierschein.app` mit `a38` wie im Release, aber ad-hoc signiert (`APP_SIGN_ADHOC=1`, `APP_CHECK=adhoc`). Der Lauf prüft Aufbau, Reihenfolge der Signatur, Bezeichner, Hardened Runtime, ZIP und SBOM. Die Developer ID und die Notarisierung brauchen die Secrets und laufen nur in `release.yml` und `signed-snapshot.yml`.
- **1Password ({{ ref("T15") }}):** der Integrationstest gegen den Vault `passierschein.dev` mit dem Service Account der CI. Der Test liest nur.

Ein Lauf dauert etwa fünf Minuten; das Release-Bundle kostet etwa eine bis zwei Minuten mehr. `app:e2e` läuft in der grafischen Sitzung des Runners; die zwei kurzen Fenster öffnen sich dort.

Nicht automatisch prüfbar bleiben der echte Dialog von Touch ID und die Sicht unter OmniWM.
Offen sind Vollbild, Wechsel des Arbeitsbereichs, Zeitablauf und Meldungen ({{ ref("G33") }}) und der Praxistest eines echten Release auf dem Mac ({{ ref("G5") }}). Der signierte Snapshot mit der echten Developer ID ist am 2026-11-12 grün ([Lauf 43208639784](https://github.com/seletz/passierschein/actions/runs/43208639784)).

## Doku auf GitHub Pages

Der Workflow `pages.yml` baut die Doku nach jedem Push auf `develop` und
veröffentlicht sie auf GitHub Pages. Der Release-Workflow veröffentlicht die
Doku nicht; online ist der Stand von `develop`. Er läuft auf Linux und ruft nur
`mise run docs:build` auf. Die Site ist öffentlich, auch wenn das Repo
privat ist. Einzelheiten stehen unter [Release](50-release.md).

### Ausgabe für Agenten (llms.txt)

Das Plugin `llmstxt` von Zensical ist ab Version 0.0.67 eingebaut.
Die Einstellung steht in `zensical.toml` unter `[project.plugins.llmstxt]`.
Der Build schreibt drei Arten von Dateien:

| Datei | Inhalt |
|---|---|
| `llms.txt` | Index mit Beschreibung und Links, gegliedert nach Diátaxis (Tutorials, Anleitungen, Referenz, Erklärung) und Design-Set |
| `<seite>/index.md` | die gerenderte Seite als Markdown, neben der HTML-Seite |
| `llms-full.txt` | alle Seiten in einer Datei |

Die Dateien stehen unter <https://seletz.github.io/passierschein/llms.txt> und <https://seletz.github.io/passierschein/llms-full.txt>.
Der Text stammt aus dem gerenderten HTML.
Die Dateien enthalten also nur, was die HTML-Seiten schon veröffentlichen.
Neue Seiten kommen über die Globs der Abschnitte automatisch hinein.
Das Skript `scripts/docs-llms-check.sh` läuft am Ende von `mise run docs:build`.
Es bricht den Build ab, wenn eine LLM-Datei fehlt, ein Link in `llms.txt` ins Leere zeigt oder ein Makroaufruf als Text erscheint.

## Kosten

In einem privaten Repository zählt eine Minute auf macOS zehnmal so viel wie eine Minute auf Linux.
Der Job läuft zudem auf einem Vorschau-Image mit wenig Kapazität ([Wenn der macOS-Job keinen Runner bekommt](#wenn-der-macos-job-keinen-runner-bekommt)).
Deshalb startet ein Pull Request den macOS-Workflow nur, wenn er einen dieser Pfade ändert:

- Go-Code: `**/*.go`, `cmd/**`, `internal/**`, `go.mod`, `go.sum`
- die Freigabe-App: `app/**`
- die Werkzeuge: `mise.toml`, `.goreleaser.yml`
- die Skripte, die der Job ausführt: `scripts/app-*.sh`, `scripts/release-app-bundle.sh`, `scripts/release-app-check.sh`, `scripts/release-app-lib.sh`, `scripts/release-app-package.sh`, `scripts/release-app-sign.sh`, `scripts/sbom-check.sh`, `scripts/onepassword-integration*.sh`, `scripts/sdk-core-check.sh`
- die Entitlements von `a38`: `scripts/a38.entitlements` ({{ ref("D59") }})
- den Workflow selbst: `.github/workflows/macos.yml`

Nicht dabei: Doku (`docs/**`), Dateien des Design-Sets, Markdown, `README.md`, `scripts/demo.sh` und die anderen Workflows (`ci.yml`, `pages.yml`, `release.yml`, `signed-snapshot.yml`).
Ein Push auf `develop`, der nächtliche Lauf und der Start von Hand laufen immer.

### Regel für den Pfadfilter und den Branch-Schutz

Ein Pfadfilter überspringt den Workflow, wenn kein Pfad passt.
GitHub zeigt dann **keine** Prüfung `macos` an.
Ist `macos` später eine erforderliche Prüfung des Branch-Schutzes, bleibt ein Pull Request ohne den Job dauerhaft auf „Expected“ und lässt sich nicht zusammenführen.

Die Regel:

- Ein Pull Request ohne den macOS-Job ist in Ordnung, wenn er keinen der Pfade oben ändert. Die Koordination prüft das mit `gh pr diff <nr> --name-only` gegen die Liste.
- Ändert ein Pull Request einen der Pfade, muss `macos` grün sein, bevor er zusammengeführt wird.
- Der Branch-Schutz von `develop` verlangt heute nur `check`. Soll `macos` erforderlich werden, ist der Pfadfilter dafür der falsche Weg: Dann läuft der Workflow bei jedem Pull Request und der Job beginnt mit einer Prüfung der geänderten Pfade (zum Beispiel `dorny/paths-filter`, gepinnt) und überspringt seine Schritte selbst. Ein Job, der übersprungen wird, zählt für den Branch-Schutz als erfüllt. Das ist eine Entscheidung für später; sie braucht den Pfadfilter nicht.
- Ändert sich die Liste der Pfade, ändern sich `macos.yml` und diese Seite im selben Pull Request.

### Zeitlimits

Jeder Job hat `timeout-minutes`; `mise run tools:check` prüft das.
Ein hängender Job kostet so höchstens das Limit.

| Workflow | Job | Limit | Üblicher Lauf |
|---|---|---|---|
| `ci.yml` | `check` | 20 Minuten | 2 bis 6 Minuten |
| `macos.yml` | `macos` | 30 Minuten | 5 bis 10 Minuten |
| `pages.yml` | `docs`, `pages` | je 10 Minuten | unter 3 Minuten |
| `release.yml` | `release` | 30 Minuten | |
| `release.yml` | `app` (macOS) | 60 Minuten | wegen der Notarisierung |
| `release.yml` | `publish` | 15 Minuten | |
| `signed-snapshot.yml` | `snapshot` | 30 Minuten | |
| `signed-snapshot.yml` | `app` (macOS) | 60 Minuten | wegen der Notarisierung |

Das Limit zählt ab dem Start auf einem Runner, nicht ab dem Warten auf einen Runner.

### Gruppen für gleichzeitige Läufe

| Workflow | Gruppe | Bei neuem Lauf |
|---|---|---|
| `ci.yml`, `macos.yml` | `ci-<PR-Nummer>`, `macos-<PR-Nummer>`; auf `develop` der Commit | Ein neuer Push auf einen Pull Request bricht den alten Lauf desselben Pull Requests ab. |
| `ci.yml`, `macos.yml` auf `develop`, nächtlich, von Hand | der Commit | Kein Lauf bricht einen anderen ab (`cancel-in-progress: false`). Jeder Commit auf `develop` behält seine volle Prüfung. |
| `pages.yml` | `pages` | Ein laufendes Deployment wird nie abgebrochen; ein weiteres wartet. |
| `release.yml` | `release-<Tag>` | Ein zweiter Lauf desselben Tags wartet. |

Die Läufe auf `develop` laufen nebeneinander, wenn Runner frei sind, und warten sonst auf einen Runner.
Eine gemeinsame Gruppe für alle Commits von `develop` würde sie der Reihe nach ausführen.
GitHub hält dann aber nur einen wartenden Lauf und verwirft die älteren; ein Commit verlöre seine Prüfung.
Deshalb gibt es eine Gruppe je Commit.

### Wenn der macOS-Job keinen Runner bekommt

Das Image `xcode-27` ist eine öffentliche Vorschau mit kleiner Kapazität.
Am 2026-11-12 wurden mehrere Jobs nach 15 Minuten abgebrochen.
Die Meldung im Lauf lautet:

```text
The job was not acquired by Runner of type hosted even after multiple attempts
```

Das ist kein Fehler des Codes. Der Job hat nie einen Schritt ausgeführt.

Was zu tun ist:

1. Den Lauf einmal wiederholen, frühestens nach 20 Minuten (`gh run rerun <id> --failed`). Ein zweiter Versuch gleich danach verschärft den Engpass.
2. Scheitert auch der zweite Versuch, nicht weiter wiederholen. Der Stand gehört in den Bericht des Pull Requests: „macOS-Job ohne Runner, zweimal“. Die Koordination entscheidet.

Ausweichmöglichkeiten, keine ist entschieden; sie sind Optionen für den Eigentümer:

| Option | Kosten und Folgen |
|---|---|
| Swift auf eine Version senken, die das Image `macos-26` (= `macos-latest`, Xcode bis 26.6) bauen kann | Das Image hat große Kapazität und ist kein Vorschau-Image. Der Preis: Die Pins in `mise.toml` (alle App-Tasks und `release:app`) ändern sich, ebenso `DEVELOPER_DIR` und `runs-on` in `macos.yml`, `release.yml` und `signed-snapshot.yml`. Die App müsste mit der älteren Sprachversion und dem älteren SDK bauen; das ist zu prüfen, bevor man es zusagt. Das Release-Bundle wird dann ebenfalls mit dem älteren SDK gebaut. |
| Self-hosted Runner auf einem eigenen Mac | Keine Minuten bei GitHub und volle Kontrolle über Xcode. Der Preis: ein Mac, der immer läuft, Pflege der Software, und die Sicherheit. Ein Runner in einem privaten Repository führt Code von Pull Requests aus. Er braucht ein eigenes Benutzerkonto ohne Zugang zum Schlüsselbund und zu `~/.config/a38`, und er darf nicht der Mac sein, auf dem der Eigentümer arbeitet. Die Secrets der Signatur lägen nicht darauf; `release.yml` kann weiter auf GitHub laufen. |
| Den Job nur nachts und auf `develop` laufen lassen | Keine Wartezeit in Pull Requests, aber ein Fehler zeigt sich erst nach der Zusammenführung. |

## Caches

Kein Cache enthält ein Secret, `dist/` oder `$RUNNER_TEMP`.
Jeder Cache nutzt die gepinnte Action `actions/cache`.

| Workflow | Cache | Schlüssel |
|---|---|---|
| beide | Werkzeuge von mise (`mise-action`, `cache: true`) | Version von mise, `mise.toml` |
| macOS | dazu die Swift-Toolchain der App-Tasks (`cache_save_post`, eigener Präfix `mise-macos-swift-v1`) | wie oben |
| beide | Go-Module und Build-Cache von Go | `go.sum`, `go.mod`, `mise.toml`, je Betriebssystem |
| CI | Cache von golangci-lint | `go.sum`, `mise.toml`, `.golangci.yml` |
| CI | Cache von uv und `.venv` | `uv.lock`, `pyproject.toml`, `mise.toml` |
| macOS | Build-Ordner von SwiftPM `app/.build` | `app/Package.swift`, `mise.toml`, Quellen der App |

`app:build` baut aus dem Cache nur, was sich geändert hat.
Der Task legt das Bundle jedes Mal neu an und prüft das neue Release-Binary.

Gemessene Laufzeit eines Jobs (2026-11-12):

| Workflow | ohne Caches | kalt (Caches leer) | warm |
|---|---|---|---|
| CI (Linux) | 300 bis 480 s | 330 s | 117 s |
| macOS | 242 bis 280 s | 248 s | 130 bis 136 s |

Der Release-Snapshot und die Prüfung der SBOMs laufen weiter bei jedem Pull Request.
Sie sind die einzige Stelle, an der ein Pull Request alle vier Ziele baut, auch darwin.
Mit dem Build-Cache dauert der Snapshot warm etwa 15 Sekunden statt 90 bis 160 Sekunden.

Einmal brauchte der Aufbau des SDK-Clients auf dem macOS-Runner mehr als 30 Sekunden, und der Integrationstest scheiterte; der nächste Lauf war grün.
Der Test erlaubt deshalb 60 Sekunden je Aufruf.
Ein Fehler im Schritt „1Password integration test“ ist trotzdem zuerst ernst zu nehmen.

## Runner und Swift

- Die App-Tasks pinnen Swift 6.4.2 (Toolchain von swift.org über mise).
- Die Toolchain braucht das macOS-SDK aus Xcode. Das passende SDK ist Xcode 27.2.
- Stand 2026-11-12: Das Image `macos-26` (= `macos-latest`) hat Xcode bis 26.6. Nur das Image `xcode-27` hat Xcode 27.2 ([runner-images](https://github.com/actions/runner-images/blob/main/images/macos/xcode-27-arm64-Readme.md)).
- Der Workflow setzt `DEVELOPER_DIR=/Applications/Xcode_27.2.app/Contents/Developer`.

Risiken:

- `xcode-27` ist bei GitHub eine öffentliche Vorschau. GitHub kann das Image ändern.
- GitHub ersetzt eine Patch-Version von Xcode durch die nächste. Dann fehlt der feste Pfad, und der Job scheitert sofort an dieser Stelle. Die Abhilfe ist ein neuer Pfad im Workflow.

## Service Account der CI

Die CI nutzt einen eigenen Service Account, getrennt vom Service Account auf dem Mac.
Er darf nur den Vault `passierschein.dev` lesen.
Der Mensch kann ihn widerrufen, ohne den Daemon auf dem Mac zu berühren.

Das Secret des Repositorys heißt `OP_SERVICE_ACCOUNT_TOKEN`.
Anlegen, Setzen und Rotieren beschreibt die Anleitung [1Password-Backend einrichten](../how-to/30-1password-backend-einrichten.md#service-account-der-ci).

Im Lauf schreibt `mise run test:onepassword:ci` das Token aus der Umgebungsvariable `OP_SERVICE_ACCOUNT_TOKEN` in eine neue Datei unter `$RUNNER_TEMP` mit dem Modus `0600`.
Das Skript gibt das Token nie aus und löscht die Datei am Ende.
Die Maskierung von Secrets im Log von GitHub ist nur eine zweite Sicherung.
Fehlt das Secret, scheitert der Schritt mit einer klaren Meldung.
Ein übersprungener Test sähe grün aus und verdeckte einen Fehler.

## Rate Limits

1Password begrenzt die Anfragen eines Service Accounts ([Rate Limits](https://www.1password.dev/service-accounts/rate-limits)):

| Konto | Lesen je Stunde und Token | Anfragen je Tag und Konto |
|---|---|---|
| Business | 10.000 | 50.000 |
| Teams | 1.000 | 5.000 |
| 1Password, Families | 1.000 | 1.000 |

Das Tageslimit gilt für alle Service Accounts eines Kontos zusammen, also für den Mac und die CI.

Schätzung für einen Lauf des Integrationstests:

- Der Test macht 12 Aufrufe des SDK: einmal die Vaults für die Prüfung der Sichtbarkeit, einmal die Vaults beim ersten Auflösen, je Referenz die Items und ein Item (3 × 2), drei Lesezugriffe und die Items für das fehlende Item. Dazu kommt die Anmeldung des Clients.
- Wie viele Anfragen ein Aufruf des SDK erzeugt, dokumentiert 1Password nicht. Mit bis zu fünf Anfragen je Aufruf sind es höchstens etwa 70 Anfragen je Lauf.
- Der Fall mit kaputtem Token nutzt kein gültiges Token. Er zählt vermutlich nicht für das Konto.

Erwartete Läufe am Tag: einer in der Nacht, einige Pushes auf `develop`, einige Pull Requests mit passenden Pfaden; zusammen selten mehr als 20.
Das sind höchstens etwa 1.400 Anfragen am Tag, meist deutlich weniger.

- Business und Teams: weit unter dem Limit.
- 1Password und Families (1.000 am Tag für das ganze Konto): Im ungünstigsten Fall reicht das Limit nicht. Dann den Workflow seltener starten, zum Beispiel ohne Pull Requests.

Den Verbrauch zeigt `op service-account ratelimit passierschein-ci` im eigenen Terminal.
